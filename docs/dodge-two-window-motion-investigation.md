# Why a Dodge client can draw 60 frames and show 20 updates per second

Investigated the Pages client at f3145169754a1fe8ac128d8b13e0dd847e4faeb4 and a private match on the live Render service. Both clients reported the authority compatibility ID cryptball-v1-3df2b27547b67bdd701a62f9. The recording shows Crypt Dodge.

## What reproduced

Two isolated headless Chromium pages joined one private room on the deployed game with diagnostics enabled. After both seats were ready, I dispatched a window blur event to the joining client before the host started the match. Both pages entered the normal play screen. I counted production diagnostic events in simultaneous four-second windows, then exercised mid-match blur and explicit return on the peer. The headless setup deliberately isolates the application reaction to the event. It allows browser frames to continue.

The 15.29-second recording contains 839 encoded video frames. To estimate visible motion independently, I tracked the bright glyphs on Kevin's overhead label against their background using the seven-second frame as a template and the encoded presentation timestamps. From seconds 6–15, 501 adjacent pairs matched confidently. The median interval between changes in label position was 53.3 ms and p90 was 55 ms. Pixel rounding, standing still and capture cadence affect this estimate. The clip shows an unobstructed court and supports snapshot-paced motion. It cannot identify the window's focus history or establish network latency.

## Where the clocks separate

- [Browser lifecycle](../packages/game-runtime/src/session/browser-lifecycle.ts) interrupts input on blur, even for a visible window. In the [host](../apps/cryptball/src/host.ts), both cancelInput and the suspension callback call online.suspend(). Only an interruption during play opens the cover menu. Focus restoration alone has no matching host action.
- beginOnlinePlay() awaits asset prewarm, then unconditionally enters play and resumes the fixed scheduler. The [online session](../apps/cryptball/src/online/session.ts) can still be suspended. Its update() and step() return early. Meanwhile [server kickoff](../apps/cryptball-server/src/model.ts) sets connected seats active and clears suspension. The user can see the normal court while UI, client, and server disagree on control.
- Authority keeps advancing at 60 ticks/s and normally [broadcasts every third tick](../apps/cryptball-server/src/room.ts). A suspended client can adopt a new pose every 50 ms. The [existing interpolator](../apps/cryptball/src/online/frame-interpolation.ts) expects adjacent predicted ticks and collapses gaps of more than one tick. In the explicit cover menu the host resets it every frame. Merely enabling that interpolator in the menu would still leave the three-tick gap.
- The [existing soak](../scripts/cryptball-network-profile.mjs) drives a logical input tape in each page. It exercises input admission, catch-up, and recovery. Its frame interval records callback cadence. Its acceptance logic does not reproduce blur before kickoff or require smooth visible displacement on a suspended peer.

## Changes in implementation order

1. **Make control state agree across kickoff and resume.** Give online suspension one owner and make repeated interrupts idempotent. At the end of prewarm reconcile current interruption state, session state and the new epoch. A still-away seat should enter visible cover and receive bot cover immediately. A player who returned during prewarm should be able to start normally with fresh neutral input. During an explicit pause, retain Return to play as the takeover action. Exercise blur and focus in lobby, countdown, prewarm, live play and rematch. Assert UI, authoritative controller activity, command counters and exactly one transition per real interruption. Include reconnect and held-action release.
2. **Give a visible, covered client smooth court playback.** Use a short ring of authoritative pose frames captured at snapshot adoption. Start a trial with two snapshot periods (100 ms) of presentation delay and sample by fractional server tick each visible frame. Interpolate athletes, balls and their holders on the same timeline. On underrun hold the last pose, count it, and rebuffer after prolonged gaps. Reset at epoch, score/round, ownership/contact discontinuities and re-entry from hidden state. Reuse pose extraction, generation checks and holder offsets. Keep the active player's existing prediction path. This trades a small spectator delay for continuous motion and sends no fictitious inputs.
3. **Gate on drawn movement.** Extend the two-browser profiler to set focus events at known phases, retain labelled per-entity positions at the actual draw boundary and report by client and control state. Run a constant-speed crossing, then stops, reversals, catches and holder transfers. For a stable 60 Hz crossing with more than one screen pixel of expected travel per frame, target p95 time between changed drawn positions under 34 ms, report longest hold and backwards jumps, and require zero inputs from the covered seat. Check both clients and repeat with roles swapped. Separately exercise real side-by-side windows, a fully occluded window, and two focused devices. Evaluate hidden clients on safe re-entry because browsers may stop requesting frames. [Chromium background policies](https://developer.chrome.com/blog/background_tabs)
4. **Investigate active remote movement separately if the two-device test fails.** Each checkpoint carries the other peer's last effective held input. Replay and local prediction reuse it until the next checkpoint. A remote reversal between packets therefore produces a wrong predicted trajectory. Record correction size by entity and state, correction resets, allocation skips, and local/remote trajectory error around reversals and ball contact. If repeated remote corrections dominate, prototype delivering accepted remote intent changes with execution tick and ownership revision, under the existing server authority. Benchmark incremental replay cost and command-to-draw latency. Psyonix describes why putting an interacting player and ball on different timelines produces misleading contacts. Its input buffering and whole-world prediction fit the active path here. Buffered playback fits a viewer with no controlled inputs. [Psyonix GDC networking slides](https://ubm-twvideo01.s3.amazonaws.com/o1/vault/gdc2018/presentations/Cone_Jared_It_Is_Rocket.pdf) · [Glenn Fiedler on snapshot interpolation](https://gafferongames.com/post/snapshot_interpolation/)
5. **Remove redundant main-thread work and measure it separately.** The host asks for a detached music observation every online tick, and the session deep-clones the authoritative state even when the snapshot stamp repeats. Allow the host to request a new observation only when match, epoch, generation or sequence changes. Preserve the existing detached-read API and its isolation tests. The session also writes the reconnect token to two sessionStorage keys on every adopted checkpoint. Cache successful key/value writes, invalidate on leave or rotation, and retry failed writes. Profile equal-duration matches with two clients and on a phone. Count clones and writes directly and compare p95/p99 frame work and long tasks.

## Hosting decision

Pages delivered the current static client. Match traffic in the reproduction used the Render room. Both clients received 20 reconciliations/s while their local prediction rates diverged, and the same peer recovered after a UI action. A hosting change would leave this lifecycle defect intact. For a residual symptom, compare identical scripted runs with the same client against loopback and Render. Capture per-peer snapshot arrival gaps, RTT, server tick/encode duration, debt and outbound backlog alongside focus and pose samples. Sustained debt or bursty server sends across peers implicate server scheduling. Regular sends with gaps isolated to one client warrant route, browser dispatch and device investigation. The short production test establishes neither peak-load capacity nor behavior on lossy Wi-Fi.
