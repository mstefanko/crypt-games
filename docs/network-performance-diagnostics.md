# Capture responsiveness diagnostics

Open the game URL with `?diagnostics=1` (or append `&diagnostics=1` to an existing query). This explicitly enables a bounded in-memory event recorder and an **Export performance** button. Reproduce the problem on the affected phone, then tap the button to download JSON. Exports contain browser/device viewport metadata, build and mode metadata provided by the host, frame events, and instrumented input/network events. They do not contain credentials or room reconnect tokens. The recorder retains the newest 12,000 events by default; append `&diagnosticEvents=100000` for a longer bounded capture (positive integer, capped at 100,000; invalid values fall back to 12,000). `dropped` reports overwritten events. A reload starts a new capture. Share the exported file with the reproduction details and whether the tab was backgrounded or rotated.

Physical event timestamps record browser capture. Separate session events record command application and render submission; these are not currently linked per physical input edge. Submission does not establish the first changed pixel or display scanout; this is **not physical input-to-photon latency**. Synthetic profiler inputs are labeled separately. Unsupported timing APIs do not prevent ordinary RAF/input event collection. Rendering work measured around JavaScript calls excludes asynchronous GPU work.

For repeatable desktop comparisons, build the authority first, then run:

```sh
npm run build:cryptball:server
PROFILE_SPORT=crypt-dodge PROFILE_SECONDS=120 PROFILE_RTT=100 node scripts/cryptball-network-profile.mjs .local-game-tests/dodge.json
```

The default uses two rendered browser pages with independent deterministic logical-tick input tapes. `PROFILE_PEER=sdk` explicitly selects the cheaper SDK peer fallback; it uses the shared accumulator and prediction-rate contract but does not render or simulate the full predicted world, so use the default browser peer for responsiveness acceptance. Other options: `PROFILE_SPORT` (all six sport IDs), `PROFILE_CPU` (Chromium CPU throttle on the primary browser only), `PROFILE_ENDPOINT` (one private cloud room), and `PROFILE_PLAY=solo` (offline comparison for any mode). Guardian automatically uses solo play because server room admission explicitly rejects it. Historical baselines require a separate full checkout of the matching client/server revision; partial source transforms are rejected. Guardian solo results do not establish online Guardian coverage.

`PROFILE_SPORT=crypt-guardian PROFILE_SECONDS=120 node scripts/cryptball-network-profile.mjs .local-game-tests/guardian-solo.json` captures the local boss encounter, all orbs, projectiles, and players.

Reports retain raw entity trajectories and input tapes for comparing players, all simultaneous balls/orbs, and Guardian objects where present. The profiler requests 100,000 events per browser; its summary reports `droppedEvents` and `retainedWindow`. If storage rolls over, distributions cover only the retained portion after warmup, not the full run. Numeric distributions use newly recorded events, never repeated copies of a last snapshot statistic. A script requests mode-aware actions; it does not prove every contact, score/reset, or special was exercised. Compare event annotations and trajectories, inspect both client reports, and confirm client/server build identities before accepting a result. The ordered TCP delay proxy models delay, not packet loss. Browser CPU throttling is not actual phone testing.

Integration: create the recorder once at host startup. Forward session performance callbacks through `onlineEvent(event, sessionScope)`; it records events and joins actual command allocation/application identities. Call `frame(rafTime, steps, workMs)` once per RAF and `submittedRender()` after stage submission. `captureInput('physical-event', event.timeStamp)` records physical captures separately. The `appliedInput` helper is used for explicitly linked synthetic profiler captures; physical-edge use would require carrying that ID through the action ledger first. Do not manufacture an application timestamp when input allocation is skipped.

Current host instrumentation records physical browser captures and exact session input-application sequence events separately. It does not yet attach a physical-event ID through the queued-action ledger; no physical event-to-application/submission latency distribution should be inferred by pairing nearest events. Synthetic profiler commands are measured separately.

For sustained online browser play across match endings, set `PROFILE_REMATCH=1 PROFILE_SECONDS=600`. The profiler clicks each browser’s Rematch button, waits for the ready lobby, and starts the next match with bots. Independent input tapes continue across epochs. This option rejects solo/SDK-peer configurations; unexpected disconnection or interruption fails the run. Compare `epochsObserved` and `activeFraction` in each client summary to confirm the run contained sustained gameplay, and check dropped-event windows before interpreting tail distributions.

Set `PROFILE_ASSERT_HEALTH=1` for an explicit acceptance gate after the JSON report is saved. This requires two online browser clients, no browser errors, joined final connection status, no post-warmup increases in resync, bot takeover, sequence-gap/expired/future/capacity rejections, and at least 50% active gameplay for runs of 60 seconds or more. Each client captures its counter baseline on the first RAF after two seconds; summaries retain baseline and final counters plus deltas. Startup counters are excluded. A failed gate exits nonzero and records reasons in `acceptance`; default runs only report. Counter gates cover the full post-warmup window even if the bounded event ring rolls over; timing distributions still describe only retained events, as reported by `retainedWindow`.

For sustained solo coverage, set `PROFILE_RESTART=1` (solo only). Guardian defaults to this behavior; set `PROFILE_RESTART=0` to capture only its first encounter. It clicks Retry Guardian/Rematch after the result screen and attaches the continuing deterministic tape to each newly created local session. Local `epochsObserved` counts session restarts; inspect `activeFraction` rather than treating idle results frames as gameplay. Example: `PROFILE_SPORT=crypt-guardian PROFILE_RESTART=1 PROFILE_SECONDS=120 node scripts/cryptball-network-profile.mjs .local-game-tests/guardian-120.json`.

A forced ownership change can legitimately cancel commands already in flight for the previous controlled athlete. The gate reports post-warmup `rejectedRevision` separately as `ownershipCancellations`; it does not require that count to be zero. Explicit revision receipts preserve the authority boundary. This count alone proves neither a lost valid action nor successful application; ownership/action regression tests must verify that invalid controls never apply and valid edges retain their intended semantics. Sequence-gap, expiry, future/capacity, resync, and bot-takeover gates remain unchanged.

Production online captures now include `command-render-submission` events. The host forwards actual allocation/application events to `onlineEvent`; the recorder joins them by online-session scope, match epoch, connection generation, and command sequence, then consumes each once after the stage render submission. These events label `source: "predicted-command"` and `physicalEventLinked: false`; their `applicationToSubmissionMs` measures the actual predicted-command application callback to the next submitted frame. Physical browser captures remain unlinked and produce no invented capture-to-submission duration. A submitted frame is not proof of first visible movement or photon latency.

## Jitter and retransmission-style recovery trials

The local proxy supports seeded uniform jitter (`PROFILE_JITTER_MS`, milliseconds in either direction) and head-of-line stalls (`PROFILE_STALL_RATE`, probability per received TCP stream chunk; `PROFILE_STALL_MS`, extra delay; `PROFILE_SEED`). Later bytes cannot overtake a stalled chunk, and no bytes are deleted. This models a retransmission-style delay, **not actual packet loss or TCP congestion control**: application chunks are not IP packets. Dropping bytes here would corrupt the WebSocket stream rather than model [TCP's reliable, ordered retransmission](https://www.rfc-editor.org/rfc/rfc9293.html). Real packet-loss qualification requires a kernel-level tool such as [Linux netem](https://man7.org/linux/man-pages/man8/tc-netem.8.html) on an isolated test network.

For a ten-minute stress/recovery trial:

```sh
PROFILE_SPORT=rift-volley PROFILE_SECONDS=600 PROFILE_RTT=150 PROFILE_CPU=4 \
PROFILE_JITTER_MS=30 PROFILE_STALL_RATE=0.02 PROFILE_STALL_MS=150 PROFILE_SEED=42 \
PROFILE_REMATCH=1 PROFILE_RECOVERY_SECONDS=60 PROFILE_ASSERT_RECOVERY=1 \
node scripts/cryptball-network-profile.mjs .local-game-tests/recovery-soak.json
```

The last 60 seconds retain the base RTT but disable jitter/stalls. After five seconds of settling, the recovery gate requires joined clients, at least 60 further allocated inputs, and zero additional expiry/future/capacity/sequence-gap rejections, resyncs or bot transitions. Sequence-gap/future/capacity increases across the whole measured trial also fail this gate. Transient expiries during impairment are retained and reported; this is not the stricter healthy-link zero-expiry gate. `recoveryAcceptance`, recovery baselines/deltas, and per-direction sampler counters make this distinction explicit. It requires two rendered online clients against the local authority. The ordinary impairment model tests additionally cover asymmetric delay, jitter, route changes and 100/250 ms stalls across all modes; they do not establish actual Wi-Fi packet-loss behavior or mobile GPU performance.

Each production `command-render-submission` also includes `allocatedAt` and `allocationToSubmissionMs`, measured from the actual command-allocation callback through prediction work and frame submission using the same command identity. This interval includes work after allocation, including prediction CPU; it excludes browser-event capture and any quantization before allocation. `applicationToSubmissionMs` starts at the later predicted-application callback. Neither interval is physical-event or display latency.
